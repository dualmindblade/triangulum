# Inbox: feedback from A-1 (B-22 lifecycle instrumentation + B-21)

Source: `docs/missions/A1-lifecycle-findings.md` `## Feedback` (Sol). Triaged
by the shift-2 coordinator. Two of these corroborate items I filed
independently the same shift, which is usually the signal that something is
real rather than a one-off annoyance.

## Strongly recommend — the one I would act on first

**1. GPU ownership is a convention, not a tool.**

Sol's words: *"Every timing run checked `play.exe` immediately before launch,
but another mission can race the check. A repo-level named mutex acquired by
every timing harness would make 'GPU clear' enforceable and record the owner
automatically."*

I hit the same hazard from the other side this shift and worked around it in
prose, by telling all four missions in their dispatch prompts not to
blanket-kill `play.exe`. Prose does not survive; a lock does. This is the
single highest-leverage process fix available right now, because **every
timing number this project produces is only as trustworthy as whoever
remembered to check.**

Related and already filed separately by me: `CLAUDE.md`'s "kill stale
processes" line is actively dangerous with concurrent missions.

## Corroborates items I filed independently this shift

**2. The Windows gate command is underspecified.** Sol found bare `bash`
resolved to a WSL shim with no distribution, and invoking Git's bash directly
lacked `dirname` until run as a login shell. Its working form:

```
C:\Program Files\Git\bin\bash.exe -lc 'cd /c/code/tri-a1/viewer && ./scripts/verify.sh'
```

I filed the path half of this (the gate table says repo root; it is
`viewer/scripts/verify.sh`). Sol found the shell half. Both belong in the same
one-line fix.

**3. Perf baselines need provenance and a same-binary control mode.** Sol:
two final runs from a 1 %-utilised GPU came back red, yet commit 1 and the
untouched base reproduced the same costs — so it had to hand-build three
binaries to prove the flags were inherited. It proposes recording driver,
power state, GPU clocks and baseline commit, or offering `--control EXE`.

I filed the same gate from the contention side (chaining the perf reel after
another reel produces a false 37 % regression). Sol's `--control EXE` idea is
the better fix: it turns a manual three-build audit into one command.

## New, and worth a mission each

**4. The instrument perturbs the clock it measures.** Serialising ~96,000
events through one stderr mutex stretched the raw replay to 274 s. Sol is
explicit that the *attribution* survives — the gap between 22.7 s unadmitted
and 31.7 ms build is orders of magnitude — but absolute wall seconds are
instrument-perturbed. Proposed fix: a bounded binary ring buffer drained after
capture. Worth doing before anyone tunes against these numbers.

**5. Broad speculative churn, unrelated to B-16.** Both traced runs admitted
~18,400 jobs and count-evicted ~15,600 **non-wanted** tiles. B-21 correctly
stops evicting *wanted* victims but does nothing about this. Sol is careful
that it is not evidence of B-16 by itself. It looks like a real efficiency
finding hiding in plain sight and deserves its own audit.

**6. Lifecycle specs must demand rejection events, not just admission
events.** Sol's own R-1 event list could not answer the question R-1 asked:
a key with `missing` and no `admit` does not name the rejecting branch. It
added a `gap_blocked` event to close that. A good lesson for any future
instrumentation spec, including one written by the same author.

## Infrastructure

**7. Worktree missions need the linked-worktree git directory writable.**
codex could not lock the index because the worktree's metadata lives at
`C:\code\triangulum\.git\worktrees\tri-a1`, outside its writable root. It
worked around this with a shadow repository plus a bundle, and I imported the
commits from that — but it costs a manual step every Sol worktree mission and
is now documented in the memory notes as a standing limitation. Worth fixing
properly if there is an easy sandbox-config answer.

## One thing Sol got right that I want recorded

**It reported that the handed-over baseline did not reproduce.** The dispatch
told it h3 was 6-for-6 STUCK; its own pre-fix run came back clean, and it said
so plainly instead of quietly building on the discrepancy. That is the correct
behaviour and it is what let me find the real story on re-measurement. See the
merge commit for what that turned out to be.
